# 기획 검토 결과를 어떻게 분류하고 결정할 것인가

이 문서는 기획 검토에서 발견한 문제를 어떤 기준으로 분류하고, 누가 결정하며, 어떤 범위가 막히는지 정의한다. 상세 객체와 상태는 [도메인 모델](../design/domain-model.md)과 [상태 모델](../design/state-model.md)을 따른다.

## 검토 기준

개발자는 현재 기획 원문을 다음 정보와 대조한다:

- 현재 코드베이스
- 이미 구현된 기능
- 기존 도메인 정책
- 관련 기획서
- 선행 작업 문서
- 이전 설계 결정
- 현재 기획 원문 내부의 조건과 결과

모든 검토 결과는 관련 기획 원문과 근거를 연결한다.

## 검토 결과를 세 축으로 분류한다

하나의 검토 항목은 발견 유형, 결정 주체, blocking 여부를 각각 기록한다. 세 속성은 독립적이다.

### 발견 유형

`finding_type`은 문제의 원인을 표현한다:

- `CODE_MISMATCH`: 현재 시스템 구조나 구현과 기획 내용이 맞지 않음
- `POLICY_CONFLICT`: 기존에 확정된 도메인 정책과 신규 기획이 충돌함
- `DOCUMENT_CONFLICT`: 다른 기획 문서의 정의와 현재 문서가 충돌함
- `LOGIC_DEFECT`: 같은 기획서 내부에서 조건이나 결과가 서로 모순됨
- `REQUIREMENT_GAP`: 구현에 필요한 조건이 정의되지 않음
- `AMBIGUITY`: 둘 이상의 방식으로 해석할 수 있음

### 결정 주체

`decision_owner`는 누가 최종 결과를 확정하는지 표현한다:

- `DEVELOPER`: 코드나 확정된 도메인 지식으로 개발자가 결정할 수 있음
- `PLANNER`: 제품 정책이나 사용자 경험에 영향을 주므로 기획자가 결정해야 함

### blocking 여부

`blocking`은 결정 전까지 실제 진행이 막히는지를 표현한다:

- `false`: 결정과 별개로 현재 작업을 계속할 수 있음
- `true`: 하나 이상의 `BlockedScope`가 존재함

예를 들어 “공휴일 처리 규칙 누락”은 `REQUIREMENT_GAP + PLANNER + blocking=true`로 표현할 수 있다. Blocker는 문제 유형이나 결정 주체가 아니라 진행 제한이다.

## 개발자가 결정하는 항목

`decision_owner=DEVELOPER`인 Finding은 개발자가 현재 코드와 확정된 정책을 근거로 결정한다.

대표 범위는 다음과 같다:

- 기존 도메인 모델 재사용
- 이미 존재하는 정책과의 통합 방식
- API 구조
- 객체 구조
- 트랜잭션 범위
- 기존 아키텍처 패턴 적용
- 중복 정책 제거
- 코드베이스 제약에 따른 구현 방식

개발 결정은 다음 정보를 남긴다:

1. 문제
2. 확인한 근거
3. 검토한 선택지
4. 각 선택지의 트레이드오프
5. 개발 권장안
6. 최종 채택안
7. 기획 원문과 최종 구현 기준의 차이

기획자는 개발 결정을 승인하지 않는다. Notion에서는 개발자가 어떤 근거로 어떤 결정을 채택했는지 확인한다.

## 기획자가 결정하는 Open Question

`decision_owner=PLANNER`인 Finding은 기획자 답변이 필요한 동안 Open Question을 가진다.

각 Open Question은 다음 정보를 포함한다:

1. **질문**: 실제로 결정해야 하는 사항
2. **발생 이유**: 현재 설계나 코드베이스에서 결정이 필요한 이유
3. **현재 상태**: 기획 원문, 기존 정책, 관련 코드가 정의한 내용
4. **선택지**: 실제로 채택할 수 있는 안
5. **트레이드오프**: 각 선택지가 제품과 개발에 미치는 영향
6. **개발 권장안**: 코드베이스, 기존 정책, 구현 복잡도, 도메인 일관성을 기준으로 한 권장안
7. **기획자 답변**: 기획자가 선택하거나 작성한 결과
8. **재검증 결과**: 개발자가 답변을 다시 검증한 결과

기획자 답변은 재검증 전까지 확정 Decision이 아니다. 충돌이 없으면 `PLANNER` Decision으로 채택한다.

## Blocker와 `BlockedScope`

`blocking=true`인 Finding에는 Blocker와 하나 이상의 `BlockedScope`를 연결한다.

Blocker는 다음 상황에서 생성할 수 있다:

- 핵심 정책이 결정되지 않음
- 서로 다른 기획서가 반대되는 동작을 요구함
- 선택지에 따라 데이터 모델이 달라짐
- 외부에 노출되는 제품 동작이 결정되지 않음
- 이미 구현한 기능과 신규 기획의 충돌을 해소해야 다음 작업을 진행할 수 있음

`BlockedScope`는 실제로 진행을 막는 범위를 표현한다:

- `FEATURE`: 해당 기능의 설계나 구현 전체
- `DESIGN`: 특정 정책, 데이터 구조, 계산 규칙
- `IMPLEMENTATION`: 특정 API, 계산 로직, 저장 로직
- `WORK_ITEM`: 테스트, 마이그레이션, 연동 같은 후속 작업

각 Blocker에는 다음 정보를 함께 남긴다:

- 발생 원인
- 결정이 필요한 내용
- 하나 이상의 `BlockedScope`
- 현재 진행 가능한 범위
- 선택지와 트레이드오프
- 개발 권장안
- 재개 조건
- 해결 결과
- 해결 후 다시 시작할 작업

하나의 Blocker가 여러 작업을 막으면 Scope를 여러 개 만든다. Blocker가 존재해도 Scope 밖의 작업은 계속 진행한다.

## 근거와 결정 이력을 보존한다

검토와 결정의 근거는 변경 가능한 최신 상태가 아니라 검토 당시 기준점에 연결한다.

- 기획 근거는 특정 `SourceSnapshot`을 참조한다
- 코드 근거는 repository, commit SHA, path를 포함한다
- 기존 정책 근거는 해당 정책을 확정한 Decision이나 최종설계 Revision을 참조한다
- 변경된 결정은 이전 Decision을 덮어쓰지 않고 supersede 관계로 보존한다

이 구조를 사용하면 현재 구현이 최초 기획 원문과 달라진 이유를 이후에도 역추적할 수 있다.
