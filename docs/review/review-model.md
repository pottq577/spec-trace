# 기획 검토 결과를 어떻게 분류하고 결정할 것인가

## 검토 기준과 분류

개발자는 현재 기획 원문을 다음 정보와 대조한다:

- 현재 코드베이스
- 이미 구현된 기능
- 기존 도메인 정책
- 관련 기획서
- 선행 작업 문서
- 이전 설계 결정
- 현재 기획 원문 내부의 조건과 결과

검토 결과는 다음 유형으로 분류한다:

- **코드베이스 불일치**: 현재 시스템 구조나 구현과 기획 내용이 맞지 않음
- **정책 충돌**: 기존에 확정된 도메인 정책과 신규 기획이 충돌함
- **문서 간 불일치**: 다른 기획 문서의 정의와 현재 문서가 충돌함
- **논리적 결함**: 같은 기획서 내부에서 조건이나 결과가 서로 모순됨
- **요구사항 누락**: 구현에 필요한 조건이 정의되지 않음
- **모호한 요구사항**: 둘 이상의 방식으로 해석할 수 있음
- **개발 결정사항**: 코드나 확정된 도메인 지식을 바탕으로 개발자가 결정할 수 있음
- **제품 결정사항**: 제품 정책이나 사용자 경험에 영향을 주므로 기획자가 결정해야 함

모든 검토 결과는 관련 기획 원문과 근거를 연결한다.

## 개발자가 결정하는 항목

코드 레벨이나 이미 확정된 도메인 지식으로 해결할 수 있는 문제는 개발자가 결정한다.

대표 범위는 다음과 같다:

- 기존 도메인 모델 재사용
- 이미 존재하는 정책과의 통합 방식
- API 구조
- 객체 구조
- 트랜잭션 범위
- 기존 아키텍처 패턴 적용
- 중복 정책 제거
- 코드베이스 제약에 따른 구현 방식

개발 결정은 결과만 기록하지 않는다. 최소한 다음 정보를 남긴다:

1. 문제
2. 확인한 근거
3. 검토한 선택지
4. 각 선택지의 트레이드오프
5. 개발 권장안
6. 최종 채택안
7. 기획 원문과 최종 구현 기준의 차이

기획자는 개발 결정을 승인할 필요가 없다.
Notion에서는 개발자가 어떤 근거로 어떤 결정을 채택했는지 확인한다.

## Open Question

제품 정책이나 사용자 경험을 개발자가 단독으로 확정할 수 없으면 Open Question으로 만든다.

각 Open Question은 다음 정보를 포함한다:

1. **질문**: 실제로 결정해야 하는 사항
2. **발생 이유**: 현재 설계나 코드베이스에서 결정이 필요한 이유
3. **현재 상태**: 기획 원문, 기존 정책, 관련 코드가 정의한 내용
4. **선택지**: 실제로 채택할 수 있는 안
5. **트레이드오프**: 각 선택지가 제품과 개발에 미치는 영향
6. **개발 권장안**: 코드베이스, 기존 정책, 구현 복잡도, 도메인 일관성을 기준으로 한 권장안
7. **결정**: 기획자가 확정한 결과

Open Question 자체에 기획자가 결정하는 데 필요한 맥락을 포함한다.

## Blocker와 blocked_scope

Blocker는 해당 결정이 없으면 설계나 개발의 특정 범위를 진행할 수 없는 검토 항목이다.
모든 Open Question이 Blocker는 아니며, 모든 Blocker가 기능 전체를 막는 것도 아니다.

Blocker는 다음 상황에서 생성할 수 있다:

- 핵심 정책이 결정되지 않음
- 서로 다른 기획서가 반대되는 동작을 요구함
- 선택지에 따라 데이터 모델이 달라짐
- 외부에 노출되는 제품 동작이 결정되지 않음
- 이미 구현한 기능과 신규 기획의 충돌을 해소해야 다음 작업을 진행할 수 있음

각 Blocker에는 `blocked_scope`를 기록한다.
`blocked_scope`는 해당 Blocker가 실제로 진행을 막는 범위를 설명한다.

`blocked_scope`는 최소한 다음 수준을 표현할 수 있어야 한다:

- **전체 기능**: 해당 기능의 설계나 구현 전체를 진행할 수 없음
- **특정 설계**: 특정 정책, 데이터 구조, 계산 규칙 등 일부 설계를 확정할 수 없음
- **특정 구현**: 특정 API, 계산 로직, 저장 로직 등 일부 구현을 진행할 수 없음
- **특정 작업**: 테스트, 마이그레이션, 연동 같은 특정 후속 작업을 진행할 수 없음

Blocker에는 다음 정보를 함께 남긴다:

- 발생 원인
- 결정이 필요한 내용
- `blocked_scope`
- 현재 진행 가능한 범위
- 선택지와 트레이드오프
- 개발 권장안
- 해결 결과
- 해결 후 다시 시작할 작업

`blocked_scope`를 사용하면 Blocker가 존재해도 영향이 없는 작업은 계속 진행할 수 있다.
기획자에게는 기술적 범위 대신 "이 결정이 없으면 무엇을 진행할 수 없는지"를 업무 언어로 보여준다.
