# 기획자에게 어떤 개발 검토 결과를 보여줄 것인가

이 문서는 기획자가 Notion에서 확인할 개발 검토의 정보 구조와 표현 원칙을 정의한다.
[문서 계획](../00_INDEX.md#문서-계획)에 따라 기획자용 표현 범위를 정하며, 페이지 생성과 답변 수집은 [Notion 검토 결과 계약](../integration/notion-review-contract.md)과 [Notion 동기화 규칙](../integration/notion-sync-rules.md)을 따른다.

## 개발 검토 페이지는 현재 할 일을 먼저 보여준다

기획자는 인공지능(AI) 분석 전문이나 개발 내부 로그를 읽지 않는다. 시스템은 개발자가 채택한 결과와 기획자가 결정해야 할 항목만 ROOT 기획 페이지 아래의 `개발 검토` 페이지에 정리한다.

기본 구조는 다음과 같다:

```markdown
# 개발 검토

## 현재 상태

기획 확인 필요

- 개발 결정: 4건
- 확인 필요: 2건
- Blocker: 1건

## 이번 검토에서 개발자가 결정한 사항

### 소수점 처리 정책

기존 근태환경설정 정책을 재사용합니다.

- 이유: 동일 정책의 중복 정의를 방지합니다
- 반영: 기존 소수점 정책을 구현 기준으로 사용합니다
```

개발 결정은 확인용이다. 기획자의 승인이나 답변을 요구하지 않는다.

## 기획자가 결정할 항목에는 답변 슬롯을 제공한다

OpenQuestion은 결정에 필요한 맥락을 같은 섹션에서 보여준다.

```markdown
## 확인이 필요한 사항

### 주 15시간 근무자의 공휴일 처리

- 현재 상태: 공휴일 처리 규칙이 정의되지 않음
- 선택 A: 주 15시간 유지
- 선택 B: 실제 근무일수에 따라 조정
- 개발 권장: 선택 A
- 이유: 기존 주간 정책과 계산 기준을 유지함

▶ 답변
```

실제 Notion에서는 `답변` toggle의 하위 블록을 기획자 소유 입력 영역으로 사용한다. 시스템은 해당 하위 블록을 수정하지 않는다.

## Blocker는 막힌 범위와 진행 가능한 범위를 함께 보여준다

기획자 결정이 필요한 Blocker는 OpenQuestion과 답변 영역을 공유한다.

```markdown
## Blocker

### 공휴일 포함 시 주간 기준시간

- 막힌 범위: 주간 기준시간 계산 로직
- 현재 가능한 작업: 조회 인터페이스, 기본 저장 구조
- 재개 조건: 공휴일 포함 시 주간 기준시간 정책 확정

▶ 답변
```

개발자가 처리할 Blocker는 답변 toggle을 만들지 않는다. 기획자에게 현재 차단 상태와 진행 가능한 업무만 전달한다.

## 변경 검토에서는 새로 달라진 내용부터 보여준다

개발 중 기획이 변경되면 과거 검토 전문을 반복해서 보여주지 않는다. 이번 변경으로 새로 생기거나 다시 열린 Decision, OpenQuestion, Blocker를 우선 표시한다.

기존 Decision이 그대로 유지되지만 이번 변경을 이해하는 데 필요하면 `유지되는 기존 결정`으로 짧게 표시한다. 전체 이력은 내부 추적 모델에서 보존한다.

## 내부 기술 근거는 필요한 수준으로 번역한다

기획자 화면은 commit SHA, 클래스명, 데이터베이스 키 같은 개발 내부 식별자를 기본으로 노출하지 않는다. 선택지와 권장안의 이유를 업무 동작, 정책 일관성, 사용자 영향 중심으로 설명한다.

개발자가 근거를 다시 확인할 때는 내부 EvidenceRef를 사용한다.
