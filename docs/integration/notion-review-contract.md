# 기획자에게 검토 결과를 어떻게 보여주고 답변을 받을 것인가

이 문서는 내부 Review, Decision, Open Question, Blocker를 Notion에 투영하고 기획자 답변을 수집하는 출력 계약을 정의한다.
[문서 계획](../00_INDEX.md#문서-계획)에 따라 기획자의 기존 기획 작성 방식은 유지하고 검토 결과만 별도 시스템 영역에 추가한다.

## 기획 문서마다 개발 검토 페이지 하나를 유지한다

시스템은 각 `PlanningDocument`의 `ROOT` 페이지 아래에 `개발 검토` 하위 페이지 하나를 생성한다. 같은 기획 문서에서 ReviewCycle이 여러 번 생겨도 이 페이지를 재사용한다.

개발 검토 페이지는 시스템 소유 출력이다. 시스템은 해당 Notion `page_id`를 내부에 저장하고 원문 수집에서 제외한다.

기획자는 원래 기획 페이지와 하위 기획 페이지를 기존 방식대로 작성한다. 개발 검토 페이지는 개발 결정 확인과 제품 결정 답변에만 사용한다.

## 개발 검토 페이지는 현재 필요한 정보만 보여준다

개발 검토 페이지는 다음 순서로 구성한다:

1. `현재 상태`
2. `이번 검토에서 개발자가 결정한 사항`
3. `확인이 필요한 사항`
4. `Blocker`
5. `현재 진행 가능한 범위`

`현재 상태`는 내부 객체 상태를 업무 언어로 요약한다. 내부 식별자, commit SHA, 코드 경로, 인공지능(AI) 분석 로그는 기본 화면에 노출하지 않는다.

개발 결정은 기획자의 승인을 요구하지 않는다. 기획자가 결정해야 하는 항목만 답변 입력 영역을 가진다.

## 시스템 소유 영역과 기획자 소유 영역을 분리한다

개발 검토 페이지의 설명, 선택지, 개발 권장안, Blocker 범위는 시스템이 관리한다. 기획자는 시스템 소유 블록을 수정하지 않는 것을 운영 규칙으로 삼는다.

Open Question마다 시스템은 `답변` toggle 블록 하나를 만든다. 이 toggle의 하위 블록만 기획자 소유 영역이다.

기획자는 `답변` toggle 안에서 문단, 목록, 링크 등 Notion 블록을 자유롭게 작성할 수 있다. 시스템은 현재 answer slot의 하위 블록을 수정하거나 삭제하지 않는다.

## Open Question은 하나의 안정적인 답변 슬롯을 가진다

시스템은 `open_question_id`와 현재 `answer_slot_block_id`를 연결한다. 같은 질문을 다시 렌더링해도 기존 답변 슬롯을 유지한다.

기획자가 답변 내용을 변경하면 시스템은 정규화한 답변 hash를 비교한다. hash가 달라졌고 내용이 비어 있지 않으면 새 `PlannerAnswer`를 만들고 이전 답변을 `supersedes_answer_id`로 연결한다.

Open Question이 해결된 뒤 다시 열리면 기존 답변은 이력으로 보존한다. 시스템은 이전 답변을 읽기 전용 요약으로 표시하고 새 빈 `답변` toggle을 만들어 현재 answer slot으로 지정한다.

## 기획자 답변은 바로 Decision이 되지 않는다

새 `PlannerAnswer`를 수집하면 Open Question 상태를 `ANSWERED`로 전환한다. 개발자가 코드베이스, 기존 정책, 관련 기획을 재검증할 때 `VERIFYING`으로 전환한다.

재검증에서 충돌이 없으면 `Decision(owner=PLANNER)`을 채택하고 Open Question을 `RESOLVED`로 전환한다. 추가 확인이 필요하면 질문을 다시 열고 새 답변 슬롯을 제공한다.

기획자는 이 과정에서 별도 개발 도구를 사용하지 않는다.

## Blocker는 결정 주체에 따라 다르게 보여준다

`decision_owner=PLANNER`인 Finding이 Blocker라면 같은 Open Question 안에서 다음 정보를 함께 보여준다:

- 결정하지 않으면 진행할 수 없는 업무
- 현재 진행 가능한 업무
- 선택지와 트레이드오프
- 개발 권장안
- 기획자 답변 영역

`decision_owner=DEVELOPER`인 Blocker는 기획자 답변 영역을 만들지 않는다. 개발자가 처리 중인 차단 항목과 현재 진행 가능한 범위만 정보로 표시한다.

하나의 Blocker에 여러 `BlockedScope`가 있으면 기획자에게는 업무 단위 설명으로 묶어서 보여준다.

## 변경 검토는 이번 변경에 필요한 내용부터 보여준다

`review_type=CHANGE`인 ReviewCycle에서는 과거 전체 검토를 다시 노출하지 않는다. 현재 변경으로 새로 생기거나 다시 열린 항목을 우선 표시한다.

기존에 유효한 개발 Decision은 필요할 때만 `유지되는 기존 결정`으로 짧게 표시한다. 전체 결정 이력과 근거는 시스템 내부 추적 모델에서 보존한다.

이 규칙은 기획자가 매 변경마다 이전 검토 전문을 다시 읽지 않게 한다.

## 시스템 소유 출력이 수정되면 다음 동기화에서 복구한다

기획자가 시스템 소유 설명 블록을 수정하거나 삭제하면 다음 출력 동기화에서 내부 확정 상태를 기준으로 복구한다. 기획자 소유 answer slot 내용은 복구 대상에서 제외한다.

기획자가 현재 answer slot 자체를 삭제하면 시스템은 새 answer slot을 만들고 삭제 사실을 동기화 이력에 남긴다. 이전에 수집한 `PlannerAnswer` 이력은 유지한다.

개발 검토 페이지 전체가 삭제되거나 archive되면 시스템은 같은 `PlanningDocument` 아래에 새 페이지를 만들고 내부 출력 매핑을 갱신한다.

## 기획자용 출력은 내부 추적 이력의 원본이 아니다

Notion 개발 검토 페이지는 현재 업무를 위한 projection이다. Finding, Decision, PlannerAnswer, Blocker의 정식 이력은 내부 모델이 보존한다.

Notion 출력 페이지를 과거 이력 저장소로 사용하지 않는다. 페이지를 다시 생성해도 내부 결정과 답변 이력은 유지되어야 한다.
