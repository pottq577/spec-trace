# 신규 설계서를 어떻게 검토하고 개발 기준으로 확정하는가

## 업무 시나리오 1: 신규 설계서를 검토하고 개발한다

이 시나리오는 기획자가 작성한 설계서를 처음 검토하고 최종설계서를 확정한 뒤 개발을 시작하는 흐름이다.

### 1. 기획자가 설계서를 작성한다

**Actor:** 기획자

기획자는 기존 방식대로 GPT 등 기존 도구로 설계서를 작성하고 결과 전문을 Notion에 등록한다.

기획자는 별도의 검토 양식이나 변경 이력을 작성하지 않는다.

### 2. 개발자가 설계서를 로컬에 확보한다

**Actor:** 개발자

개발자는 Notion 설계서를 Markdown 작업본으로 저장한다. 이 문서는 코드베이스와 관련 문서를 대조하기 위한 입력 자료다.

Notion에서 로컬로 가져오는 구체적인 방식은 이후 구현 설계에서 결정한다.

### 3. 개발자가 AI와 함께 설계서를 검수한다

**Actor:** 개발자 + AI

개발자는 다음 자료를 함께 검토한다:

- 현재 코드베이스
- 이미 구현된 선행 기능
- 기존 도메인 정책
- 관련 설계서
- 이전 개발 결정
- 현재 설계서 내부의 조건과 결과

검수 결과는 개발자가 결정할 항목, 기획자가 결정할 Open Question, 개발 진행을 막는 Blocker로 연결한다.

### 4. 개발자가 결정 가능한 항목을 확정한다

**Actor:** 개발자 + AI

코드베이스, 선행 작업, 기존 정책, 도메인 지식만으로 판단할 수 있으면 개발자가 결정한다.

예시는 다음과 같다:

- **문제**:
  - 기획서에서 새로운 소수점 처리 정책을 정의함
- **근거**:
  - 근태환경설정에서 같은 정책이 이미 확정됨
- **선택지**:
  - A. 현재 설계서 기준으로 별도 정책 추가
  - B. 기존 근태환경설정 정책 재사용
- **개발 권장**:
  - B
- **채택**:
  - 기존 근태환경설정 정책 재사용
- **설계서와의 차이**:
  - 현재 설계서의 별도 소수점 정책은 구현 기준에서 제외

이 항목은 기획자의 승인을 기다리지 않는다.
기획자에게는 판단 근거와 채택 결과를 확인용으로 제공한다.

### 5. 제품 결정이 필요한 항목을 Open Question으로 만든다

**Actor:** 개발자 + AI

제품 정책이나 사용자 경험을 개발자가 확정할 수 없으면 Open Question으로 만든다.

예시는 다음과 같다:

- **질문**:
  - 주 15시간 근무자에게 공휴일이 포함되면 주간 기준시간을 어떻게 계산해야 하는가?
- **발생 이유**:
  - 현재 설계서에 공휴일 처리 규칙이 없음
- **선택지**:
  - A. 공휴일과 관계없이 15시간 유지
  - B. 실제 근무 가능 일수에 따라 조정
- **개발 권장**:
  - A
- **기획 결정**:
  - 답변 대기

기획자는 질문, 선택지, 트레이드오프, 개발 권장안을 보고 제품 정책을 결정한다.

### 6. 개발을 막는 항목에 Blocker를 지정한다

**Actor:** 개발자 + AI

Open Question이나 검토사항 중 결정 없이는 특정 작업을 진행할 수 없는 항목에 Blocker를 지정한다.

Blocker에는 `blocked_scope`를 함께 기록한다.

예시는 다음과 같다:

- **Blocker**:
  - 주 15시간 근무자의 공휴일 처리 방식 미확정
- **blocked_scope**:
  - 주간 기준시간 계산 로직 설계 및 구현
- **현재 진행 가능**:
  - 근무유형 조회 API
  - 기본 저장 구조
- **해결 조건**:
  - 공휴일 포함 시 주간 기준시간 정책 확정

개발자는 `blocked_scope` 밖의 작업을 계속 진행할 수 있다.

### 7. 개발자가 검토 명세서를 확정한다

**Actor:** 개발자 + AI

개발자는 지금까지의 검토 결과를 로컬 문서에 명세한다.

검토 명세서는 상세 근거를 보존하고 이후 재검증의 기준으로 사용한다.

### 8. 시스템이 기획자용 개발 검토를 Notion에 작성한다

**Actor:** 시스템

시스템은 기존 설계서와 연결된 위치에 기획자용 결과를 작성한다.

기획자는 다음 정보만 확인한다:

- 현재 상태
- 개발자가 결정한 사항
- 자신이 확인해야 하는 Open Question
- Blocker
- Blocker가 막고 있는 업무 범위

기획자는 Notion의 기획자용 개발 검토만 확인한다.

### 9. 기획자가 필요한 항목에 답변한다

**Actor:** 기획자

기획자는 개발 결정은 확인하고, 제품 결정이 필요한 Open Question과 Blocker에 답변한다.

Notion 밖의 별도 도구나 개발 시스템에 접속할 필요가 없다.

### 10. 개발자가 기획자 답변을 재검증한다

**Actor:** 개발자 + AI

개발자는 기획자의 답변을 코드베이스, 기존 정책, 다른 설계 결정과 다시 대조한다.

답변으로 추가 충돌이나 새로운 질문이 생기면 해당 항목만 다시 검토한다. Open Question은 답변만으로 종료하지 않고 재검증이 끝난 뒤 확정한다.

Blocker가 해결되면 `blocked_scope`에 묶여 있던 작업을 다시 진행할 수 있다.

### 11. 개발자가 최종설계서를 확정한다

**Actor:** 개발자

구현에 필요한 정책과 Blocker가 정리되면 최종설계서를 확정한다.

최종설계서는 다음 정보를 반영한다:

- 기획 원문
- 개발 결정
- 기획자 결정
- 기존 정책
- 코드베이스 제약

기획 원문은 그대로 보존한다.

### 12. DevFlow로 개발한다

**Actor:** 개발자 + DevFlow

개발자는 최종설계서를 DevFlow의 입력 기준으로 사용해 계획, 구현, 검증을 진행한다.
