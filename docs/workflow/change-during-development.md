# 개발 중 설계서가 변경되면 어떻게 대응하는가

## 업무 시나리오 2: 개발 중 기획서가 수정된다

이 시나리오는 최종설계서를 기준으로 개발하는 중 기획자가 새로운 기획 원문을 Notion에 등록한 경우를 다룬다.

### 1. 기획자는 기존 방식으로 설계서를 수정한다

**Actor:** 기획자

기획자는 GPT 등 기존 도구로 내용을 수정하고 새로운 전문을 Notion에 등록한다.

변경점 작성, 버전 번호 입력, Diff 생성, 변경 영향도 작성, 기존 개발 결정 확인, 개발자용 변경 요청서 작성은 개발자와 시스템이 담당한다.

### 2. 시스템이 새로운 기획 원문을 감지한다

**Actor:** 시스템

시스템은 현재 개발 기준을 만든 기획 원문 이후 새로운 원문이 등록됐음을 개발자에게 알린다.

구체적인 감지 방식은 이후 구현 설계에서 결정한다.

### 3. 이전 원문과 신규 원문의 의미 변화를 확인한다

**Actor:** 시스템 + 개발자 + AI

첫 번째 비교는 기획자가 실제로 바꾼 내용을 찾기 위한 원문 변경 비교(Source Diff)다.

- 비교 대상: `이전 기획 원문`, `신규 기획 원문`

이 비교는 문장 수나 줄 단위 변경량보다 정책과 요구사항의 의미를 기준으로 한다.

결과는 다음 유형으로 정리한다:

- 정책 변경
- 요구사항 추가
- 요구사항 삭제
- 조건 변경
- 표현 변경이며 의미는 유지
- 현재 개발과 무관한 변경

원문 변경 분석에는 이전 원문과 신규 원문의 근거를 함께 연결한다.

### 4. 신규 기획이 현재 개발에 미치는 영향을 분석한다

**Actor:** 개발자 + AI

두 번째 비교는 신규 기획이 현재 구현 기준에 미치는 영향을 찾기 위한 영향 분석(Impact Analysis)이다.

- `신규 기획 원문` 대비
  - `현재 최종설계서`
  - `기존 개발 결정`
  - `기존 기획자 결정`
  - `현재 코드베이스`
  - `선행 작업`
  - `관련 설계서`

영향 분석은 다음 항목을 확인한다:

- 기존 최종설계서와 충돌하는가
- 기존 개발 결정이 더 이상 유효하지 않은가
- 이미 해결된 Open Question을 다시 확인해야 하는가
- 새로운 Open Question이 생겼는가
- 새로운 Blocker가 생겼는가
- 이미 구현한 코드 수정이 필요한가
- 진행 중인 작업 중 무엇이 중단되는가

### 5. 기존 결정 중 영향받은 항목만 다시 검토한다

**Actor:** 개발자 + AI

변경과 관계없는 기존 결정은 유지한다.
의미가 바뀐 정책과 연결된 결정만 재검토 대상으로 연다.

예시는 다음과 같다:

- **신규 기획 변경**:
  - 주 15시간 선택지 삭제
- **영향받은 결정**:
  - 15시간 근무유형을 기존 WeeklyPolicy 구조로 관리
- **판정**:
  - 재검토 필요

기존 소수점 정책처럼 변경과 관계없는 결정은 그대로 유지한다.

### 6. 새로운 Blocker의 blocked_scope를 정한다

**Actor:** 개발자 + AI

변경으로 특정 설계나 구현을 계속할 수 없으면 Blocker를 생성하고 `blocked_scope`를 기록한다.

예시는 다음과 같다:

- **Blocker**:
  - 15시간 근무유형 삭제 후 기존 데이터 처리 정책 미확정
- **blocked_scope**:
  - 기존 15시간 데이터 마이그레이션
- **관련 수정 API**:
  - 배포 전 데이터 검증
- **현재 진행 가능**:
  - 40시간 근무유형 관련 구현
  - 공통 조회 로직

개발자는 신규 기획 변경 때문에 전체 개발을 일괄 중단하지 않는다.
`blocked_scope`에 포함된 작업만 보류한다.

### 7. 신규 검토 결과를 기존 검토 흐름에 반영한다

**Actor:** 개발자 + AI

영향받은 항목은 시나리오 1과 같은 방식으로 처리한다:

1. 개발자가 결정 가능한 기술적 항목을 확정한다
2. 제품 결정이 필요한 항목을 Open Question으로 만든다
3. 진행을 막는 항목에 Blocker와 `blocked_scope`를 지정한다
4. 검토 명세서를 갱신한다
5. 기획자용 개발 검토를 갱신한다

### 8. 기획자에게 이번 변경으로 필요한 내용만 보여준다

**Actor:** 시스템

Notion에는 변경으로 새로 발생하거나 다시 열린 항목을 중심으로 보여준다.

예시는 다음과 같다:

```markdown
# 개발 검토

## 현재 상태

기획 변경 확인 필요

## 이번 기획 변경

- 주 15시간 근무유형 삭제
- 휴게시간 적용 조건 변경

## 변경에 따른 개발 결정

- 기존 15시간 정책 관련 구현을 제거합니다

## 확인이 필요한 사항

- 기존 15시간 근무 데이터 처리 방식

## Blocker

- 막힌 범위: 기존 데이터 마이그레이션, 관련 수정 API
- 현재 가능한 작업: 공통 조회 로직, 40시간 근무유형 구현
```

개발자와 시스템이 전체 Diff와 결정 이력을 추적한다. 기획자는 이번 변경에 따른 개발 결정과 자신이 결정할 항목을 확인한다.

### 9. 기획자 답변을 재검증한다

**Actor:** 개발자 + AI

개발자는 기획자 답변을 다시 검증하고 필요한 경우 관련 Open Question이나 Blocker를 갱신한다.

Blocker가 해결되면 해당 `blocked_scope`를 해제하고 중단했던 작업을 다시 진행한다.

### 10. 최종설계서를 갱신하고 개발을 계속한다

**Actor:** 개발자 + DevFlow

개발자는 신규 기획, 기존 최종설계서, 이번 개발 결정, 이번 기획자 결정을 반영해 최종설계서를 갱신한다.

DevFlow의 개발 기준도 갱신된 최종설계서로 변경한다.
