# 기획 검토부터 개발까지 업무는 어떻게 진행되는가

## 전체 업무 흐름

신규 기획서와 개발 중 변경은 같은 검토 구조를 사용한다. 변경이 발생하면 기존 검토를 처음부터 반복하는 대신 실제 변경점과 영향받은 결정부터 다시 검토한다.

1. 기획자가 Notion에 기획 원문 작성
2. 개발자가 로컬 작업본 확보
3. 코드 / 정책 / 선행 문서와 대조
4. 검토 명세서 작성
5. 개발 결정 / Open Question / Blocker 분류
6. 기획자용 개발 검토를 Notion에 제공
7. 기획자 답변과 개발자 재검증
8. 최종설계서 확정
9. DevFlow로 개발
10. 기획 원문 변경 감지
11. 변경 의미와 개발 영향 분석
12. 영향받은 검토 항목 재검토
13. 최종설계서 갱신 후 개발 계속

## 검토와 결정의 반복 규칙

기획자 답변은 즉시 최종 결정으로 취급하지 않는다. 개발자는 답변을 현재 코드베이스, 기존 정책, 관련 설계와 다시 대조한다.

검토 반복은 다음 순서를 따른다:

1. Open Question 또는 Blocker
2. 기획자 답변
3. 개발자 재검증
4. 충돌 없음
5. 결정 확정

## 검토와 결정의 반복 규칙

기획자 답변은 즉시 최종 결정으로 취급하지 않는다. 개발자는 답변을 현재 코드베이스, 기존 정책, 관련 설계와 다시 대조한다.

검토 반복은 다음 순서를 따른다:

1. Open Question 또는 Blocker
2. 기획자 답변
3. 개발자 재검증
4. 충돌 없음
5. 결정 확정

재검증에서 새로운 충돌이나 누락이 발견되면 관련 항목을 다시 열고 필요한 정보만 기획자에게 전달한다.

## 상태 판단의 기본 원칙

상태명과 저장 구조는 이후 상세 설계에서 확정한다. 현재 단계에서는 업무 의미만 정의한다.

- **검토 대기**: 새로운 기획 원문이 있고 개발 검토가 시작되지 않음
- **검토 중**: 개발자가 코드와 정책을 대조하는 중
- **기획 확인 필요**: 기획자가 결정해야 하는 Open Question이나 Blocker가 있음
- **재검증 중**: 기획자 답변을 개발자가 다시 검토하는 중
- **검토 완료**: 구현에 필요한 결정이 확정됨
- **개발 중**: 확정된 최종설계서를 기준으로 DevFlow 작업이 진행 중
- **변경 재검토**: 개발 중 신규 기획 원문이 등록되어 영향 분석이 필요함

상태는 기획자에게 필요한 수준으로 축약해 표시할 수 있다.
시스템 내부 상태와 기획자용 상태를 동일하게 만들 필요는 없다.
